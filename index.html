Anatomy of one PR

一个 PR 数据里，到底存了什么？

数据不是把 GitHub 页面简单拼接起来。它保留四个层次：原始事实、关联上下文、 模型增强结果和最终训练文本。下面的字段均来自当前 Parquet schema。

01RAW PR

原始变更事实

回答“谁在什么仓库提交了多大的变更”。

  • repo_id · repo_name
  • pr_number · title · body
  • author · author_type · merged_at
  • files / additions / deletions
  • extensions_list · py_files_count
02ENRICHED

补齐工程上下文

回答“为什么改、周围代码是什么、改动如何演进”。

  • repo_description
  • related_issue + comments
  • changed_py_files
  • relevant_files[] + content
  • commits[] + diffs[] + patch
03LLM ENHANCED

把变更讲清楚

在事实层上增加两类模型生成的结构化语义。

  • pr_summary
  • commits[].refined_message
  • 保留原始 issue、文件和 patch
  • 不覆盖原 commit message
04TASK 6

渲染为训练样本

按稳定模板组织成长文本，保留可追溯的结构边界。

  • Repository context
  • Issue discussion
  • PR intent + summary
  • Relevant source files
  • Commit history + patches

NESTED SCHEMA

关联对象不会被压扁

Issue 评论、commit 和 diff 都以嵌套结构保存，因此同一个 PR 内仍能恢复讨论时序、 commit 边界和文件级 patch。最终文本只是其中一种渲染，不是唯一交付形态。

Selection & provenance

样例怎么选，数字怎么看

01

先做平衡候选池

四个批次各取 384 条，共 1,536 条候选，避免大批次自然淹没小批次。

02

按信息密度初筛

优先有 issue、讨论、测试、多个相关文件、refined commit 与非空 patch 的 PR。

03

主动拉开多样性

人工复核任务类型、语言、批次与长度；保留小而精的 bug，也保留复杂长上下文。

04

不把精选当总体评估

这 16 条用于解释数据能力，不代表全量质量分布；规模数字来自全量联合键统计。
